# Tusk Skeleton and Application Bootstrap Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the official Tusk skeleton use `bootstrap/app.php` as its public application composition root while the Go Engine generates and runs `.tusk/runtime/worker.php` through RoadRunner.

**Architecture:** Implement the PHP application contract first, then make the framework's RoadRunner adapter consume it, and finally change the Go Engine to generate and invoke the internal worker. `tusk.json` remains platform configuration, `config/*.php` remains application configuration, and the native NDJSON runtime is removed from the default path.

**Tech Stack:** PHP 8.2+, Composer, PSR-7, RoadRunner HTTP 4.x, Go 1.23, Go YAML v2, PHPUnit 10, Go testing, Docker.

**Spec:** `docs/superpowers/specs/2026-10-04-tusk-skeleton-bootstrap-design.md`

## Global Constraints

- `bootstrap/app.php` returns a configured Tusk application and does not start a server.
- `.tusk/runtime/worker.php` is generated by the Engine and is not a user-edited application entrypoint.
- RoadRunner is the only default server path; there is no silent fallback to `NativeLoopAdapter` or an echo worker.
- RoadRunner owns HTTP, Goridge, workers, pooling, recycling, and process-level shutdown.
- The PHP application is created once per worker; request-scoped services are reset after every request.
- `tusk.json` owns Engine/platform settings; `config/*.php` owns application configuration; `composer.json` remains dependency and lockfile authority.
- Generated files must stay inside the project `.tusk` directory and must never overwrite user-owned `bootstrap/`, `config/`, or `routes/` files.
- Existing legacy workers are handled through explicit migration diagnostics, not implicit runtime selection.

## Review Focus

- Missing `bootstrap/app.php` must fail before RoadRunner accepts traffic with the project path and a corrective command; pinned by Task 4 and Task 5 tests.
- A bootstrap returning the wrong value must fail with a type-specific message and must not start a worker; pinned by Task 1 and Task 5 tests.
- A generated worker path or project root containing traversal/unsafe input must not write outside `.tusk/runtime`; pinned by Task 4 tests.
- A generated RoadRunner worker must never instantiate `NativeLoopAdapter`, read NDJSON, or start a second worker pool; pinned by Task 2 and Task 5 tests.
- Request-scoped state and shutdown hooks must be isolated across persistent requests and executed exactly once; pinned by Task 2 tests and the skeleton smoke test in Task 8.

The Engine and Framework changes are one coordinated rollout rather than independent features: the generated worker depends on the PHP Application contract. Each task below still ends with an independently testable commit.

## Completion Criteria

- A newly generated project has `bootstrap/app.php`, `config/`, `routes/`, `public/index.php`, and no user-authored runtime loop.
- `tusk start` generates `.tusk/runtime/worker.php` and passes it to RoadRunner.
- The generated worker loads the Application and uses the RoadRunner adapter.
- Missing or invalid bootstrap files fail before RoadRunner accepts traffic.
- No default path instantiates `NativeLoopAdapter` or the Engine repository's legacy worker.
- Request-scoped services reset between persistent requests and shutdown hooks run exactly once per worker.
- Docker, README, migration diagnostics, and CI all describe the same skeleton.
- `go test ./...`, `go vet ./...`, `go build -mod=readonly -buildvcs=false ./...`, and the PHP test/static-analysis suite pass.
